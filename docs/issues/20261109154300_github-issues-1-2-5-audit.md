## Effects

### Issue #2 — Job silences exceptions

| Field | Content |
|-------|---------|
| Severity | High (failed migrations stay invisible to Sentry and similar reporters) |
| Confidence | High |
| Location | `lib/data_migration/job.rb` (`discard_on StandardError`) |
| Why it matters | `discard_on` rescues the error inside ActiveJob after the task is marked failed, so host error reporters that listen for raised job failures never see it |
| Kind | Observed fact (`discard_on StandardError` is present; RFC 0006 documents that path) |
| Smallest credible fix | Remove `discard_on StandardError`; keep task `failed` + re-raise so adapters and reporters receive the exception |
| Deeper fix | Optional `after_discard` reporting hook if a host still wants discard semantics |

Missing coverage: no example asserts that a raised migration error remains visible to ActiveJob / is not discarded. Futile coverage: none for this claim.

### Issue #1 — Operator missing on `.perform_later`

| Field | Content |
|-------|---------|
| Severity | Medium (audit trail and monitoring lose the human operator on async runs) |
| Confidence | High |
| Location | `lib/data_migration/task.rb` (`perform_later` / `perform_now` / `prepare`); `lib/data_migration/config.rb` (`monitoring_context`) |
| Why it matters | `operator:` in kwargs is forwarded to the job, not to the Task row; `ActionReporter.current_user \|\|= migration.operator` lets ambient resolver state win over the stored operator |
| Kind | Observed fact (create path ignores kwargs operator; monitoring uses `\|\|=`) |
| Smallest credible fix | Extract `operator` from kwargs or `operator_resolver` before enqueue; assign monitoring current user from the Task operator |
| Deeper fix | Persist operator GlobalID in job kwargs as a redundant copy for backends that dump kwargs only |

Missing coverage: no example that `DataMigration.perform_later(name, operator: user)` stores `task.operator`. Futile coverage: monitoring specs only cover the `current_user` nil path.

### Issue #5 — Documented `db:migrate:data` cannot run

| Field | Content |
|-------|---------|
| Severity | High (README, generator USAGE, and RFC 0004 advertise a command the gem does not ship) |
| Confidence | High |
| Location | No `.rake` / Railtie under `lib/`; `lib/generators/templates/data_migration.rb.tt`; `README.md`; `rfcs/0004-operator-run-path.md` |
| Why it matters | Operators cannot run the documented shell path; README checklist still marks shell run unchecked |
| Kind | Observed fact (package has no rake task; template uses positional name) |
| Smallest credible fix | Ship `db:migrate:data` via Railtie; accept `VERSION=` / `NAME=`; update template, README, RFC 0004 |
| Deeper fix | When invoked with no selector, list migrations and task statuses |

Missing coverage: no rake / Railtie examples. Boundary mode: operator command path is the control surface; wrong docs are an unsafe “command not provided” for the advertised action.
